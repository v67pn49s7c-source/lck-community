## 요약

- 가장 급한 문제는 세 가지입니다. 비회원도 가짜 공지·운영자 사칭 글을 넣을 수 있고, 글·투표의 ID를 이용한 저장형 XSS 경로가 있으며, 예측·평점·팬심 투표는 남의 행을 덮어쓸 수 있게 정책이 작성돼 있습니다.
- 운영 DB에는 `pom_awards`와 `awards` 테이블이 실제로 없어 POM·수상 기능이 빈 데이터로 동작합니다. 반면 `profiles.is_admin`은 익명 REST 요청으로 실제 노출됐습니다.
- 경기 결과의 순위 반영은 두 번의 독립 저장이라 한쪽만 실패하면 누락 또는 이중 반영됩니다. 대부분의 낙관적 저장도 실패를 사용자에게 알리지 않습니다.

- 코드 문법과 정적 반응형 규칙은 확인했지만, 이 세션에 연결 가능한 브라우저가 없어 375/390/414/768px 및 라이트 모드의 실제 화면은 확인하지 못했습니다. 운영 DB에는 HEAD/GET만 보냈고 쓰기 요청은 하지 않았습니다.

### [P0] 비회원이 사이트 전체에 가짜 공지와 운영자 사칭 글을 만들 수 있음

- **어디**: `supabase/schema5_fav_team.sql:11-18`, `supabase/schema.sql:49-59`, `assets/board.js:5-10`, `assets/board.js:261-272`
- **무엇이 문제인가**: 비회원 글쓰기 정책은 제목·본문 길이와 팀 게시판 조건만 검사합니다. `nick`, `cat`, `author_team`, `match_id`는 검사하지 않아 REST 요청을 직접 보내면 닉네임을 `운영자`, 분류를 `공지`, 응원팀 배지를 원하는 팀으로 지정할 수 있습니다.
- **어떻게 확인했나**: 저장소 정책의 `with check` 조건을 읽었습니다. 화면은 `공지` 선택을 숨기지만 서버 정책에는 같은 제한이 없습니다. 또 팀 게시판은 `p.cat === "공지"`인 글을 팀과 무관하게 모두 섞으므로 가짜 공지가 모든 팀 게시판에 노출됩니다. 운영 데이터 보호를 위해 실제 INSERT 재현은 하지 않았습니다.
- **실제 피해**: 누구나 공식 공지처럼 보이는 피싱·사칭 글을 전체 및 모든 팀 게시판에 게시하고, 특정 팀 팬 배지를 가장할 수 있습니다.
- **제안**: 공지는 관리자만, 회원 글의 닉네임·응원팀은 `auth.uid()`의 프로필 값과 일치할 때만 허용하세요. 비회원 글을 계속 허용한다면 `cat <> '공지'`, `author_team is null`, `match_id is null`, 금지 닉네임 검사를 RLS 또는 `security definer` RPC에 넣어야 합니다. 가장 안전한 형태는 클라이언트의 임의 행 INSERT를 막고 `create_post(...)` RPC 한 곳에서 값을 정하는 것입니다.

### [P0] 공개 입력의 ID로 방문자 브라우저에서 저장형 XSS를 실행할 수 있음

- **어디**: `assets/board.js:37-49`, `assets/app.js:639-653`, `live.html:125-135`, `supabase/schema.sql:49-50`, `supabase/schema7_fanpulse.sql:6-16,68-70`
- **무엇이 문제인가**: 제목·본문·닉네임은 대체로 `esc()`를 잘 통과하지만, `posts.id`는 링크의 `href`에, `polls.id`는 HTML `id` 속성에 그대로 들어갑니다. 두 컬럼은 임의 문자열이고 서버에 안전한 문자 제약이 없습니다.
- **어떻게 확인했나**: 예를 들어 직접 REST INSERT에서 글 ID를 `x\"><img src=x onerror=...>`처럼 만들면 `href="post.html?id=${p.id}"` 템플릿을 탈출할 수 있습니다. 글은 익명 INSERT가 가능하고, 투표는 일반 회원 INSERT가 가능하므로 공격 경로가 열려 있습니다. 실제 악성 데이터는 넣지 않았습니다.
- **실제 피해**: 공격 글이 홈이나 게시판에 보이는 순간 방문자의 로그인 토큰 범위에서 임의 스크립트가 실행될 수 있습니다. 관리자 방문 시 관리자 권한 요청을 대신 보내는 공격으로 이어질 수 있습니다.
- **제안**: 화면에서는 URL 값에 `encodeURIComponent()`를 적용하고 속성 전체를 `esc()`하며, 투표 컨테이너는 DB ID를 HTML로 조립하지 말고 DOM으로 만든 뒤 참조하세요. DB에도 ID 형식을 제한하는 체크를 추가하세요. 예: `check (id ~ '^[A-Za-z0-9_-]{1,80}$')`. 기존 행이 모두 조건을 만족하는지 먼저 조회한 뒤 적용해야 합니다. 관리자 전용 데이터의 ID와 경기 상세 JSON 값도 같은 원칙으로 방어하면 좋습니다.

### [P0] 남의 예측·평점·팬심 투표를 덮어쓰거나 반응을 삭제할 수 있음

- **어디**: `supabase/schema.sql:137-140`, `supabase/schema7_fanpulse.sql:72-89`, `assets/store.js:364-410,630-703`
- **무엇이 문제인가**: `predictions`, `ratings`, `poll_votes`의 UPDATE 정책이 `using (true)`이고 INSERT도 행의 `voter`를 현재 사용자와 묶지 않습니다. `reactions`는 누구나 INSERT와 DELETE가 가능합니다. 공개 SELECT로 키를 알아낸 뒤 다른 사람의 값을 바꾸거나 지울 수 있는 구조입니다.
- **어떻게 확인했나**: SQL 정책을 전수 확인했습니다. 운영 DB에는 읽기 요청만 했으며 현재 `predictions` 13행, `ratings` 32행, `poll_votes` 7행, `reactions` 2행이 익명 SELECT에 노출됨을 확인했습니다. 실제 UPDATE/DELETE는 하지 않았습니다.

### [P1] 운영 DB의 실제 RLS 세대를 저장소만으로 확정할 수 없음

- **어디**: `supabase/schema.sql:143-150`, `supabase/schema2_visitor_login.sql:29-46`, `supabase/schema_remaining.sql:34-50`, `supabase/schema6_logo_settings.sql:10-14`
- **무엇이 문제인가**: 최초 SQL은 로그인한 누구나 경기·선수·전적을 수정하고 글·댓글을 삭제할 수 있게 만들고, 후속 SQL은 같은 이름의 정책을 삭제한 뒤 `is_admin()`으로 교체합니다. 어떤 SQL을 운영에 어디까지 실행했는지 저장소에는 마이그레이션 이력이 없습니다.
- **어떻게 확인했나**: 공개 REST로 `pg_policies`는 읽을 수 없어 실제 운영 정책을 확인할 수 없습니다. 후속 스키마 중 `awards`가 운영에 빠진 사실도 확인되어 “모든 후속 SQL이 적용됐다”고 가정할 수 없습니다.
- **실제 피해**: 오래된 정책이 남아 있다면 가입만 한 일반 회원이 경기 결과, 선수, 순위, 상세 기록을 바꾸거나 커뮤니티 데이터를 삭제할 수 있습니다. `site_settings` 정책이 빠졌다면 로고·중계 링크 바꿔치기도 가능합니다.
- **제안**: 사용자가 Supabase SQL Editor에서 아래 읽기 전용 쿼리를 실행해 결과를 보관하세요. `admin_write_*`와 `admin_write_settings`의 `qual`/`with_check`가 반드시 `is_admin()`이어야 합니다. 확인 뒤 현재 상태를 한 개의 기준 마이그레이션 파일로 만들고 적용 체크리스트를 두세요.

```sql
select schemaname, tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname in ('public', 'storage')
order by schemaname, tablename, policyname;

select n.nspname as schema_name, c.relname as table_name,
       c.relrowsecurity as rls_enabled, c.relforcerowsecurity as rls_forced
from pg_class c
join pg_namespace n on n.oid = c.relnamespace
where n.nspname = 'public' and c.relkind = 'r'
order by c.relname;
```

### [P1] 공개 데이터만으로 회원의 투표·평점·응원팀을 서로 연결할 수 있음

### [P1] 대부분의 저장 실패가 화면에 성공처럼 남음

- **어디**: `assets/store.js:31,195-225,239-246,304-355,364-410,521-554,587-607,630-755`
- **무엇이 문제인가**: 쓰기 함수 대부분은 캐시를 먼저 바꾸고 실패 시 콘솔에만 기록합니다. 투표·평점·댓글·반응·관리자 저장은 실패 알림과 원복이 없습니다. 글 작성만 예외적으로 저장 완료를 기다립니다.

- **무엇이 문제인가**: 인증·스냅샷·경기·게시판·예측·평점·수상·설정이 한 전역 파일에 있어 변경 충돌과 영향 범위가 큽니다. 반면 현재 파일은 기능 구역 주석이 잘 나뉘고 빌드 없는 구조에서는 단일 파일이 단순하다는 장점도 있습니다.
- **어떻게 확인했나**: 함수 책임과 호출 관계를 검토했습니다. 눈에 띄는 대규모 죽은 코드는 확인하지 못했고, CSS 미사용 여부는 동적 클래스가 많아 브라우저 coverage 없이 확정하지 않았습니다.
- **실제 피해**: 기능이 더 늘면 한 수정이 모든 페이지 데이터 부팅에 영향을 주고 리뷰가 어려워집니다.
- **제안**: 지금 당장 대규모 리팩터링하지 말고, 먼저 공통 mutation/error 계층과 서버 RPC를 정리하세요. 이후 `store-core.js`, `store-community.js`, `store-admin.js` 정도로 전역 API를 유지한 채 script 순서로 분리할 수 있습니다. 18개 HTML의 참조 관리 비용을 줄이는 방안도 함께 정해야 합니다.
