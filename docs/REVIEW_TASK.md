# 점검 의뢰서 (Codex용)

이 문서는 **사이트 전체 분석·점검**을 맡기기 위한 작업 지시서입니다.
먼저 `AGENTS.md`(작업 규칙)와 `docs/AI_HANDOFF.md`(현재 상태)를 읽고 시작하세요.

## 이번 작업의 성격

- **분석과 보고가 목적입니다. 코드를 고치지 마세요.**
  고칠 것이 보이면 보고서에 "제안 패치"로 적고, 실제 수정은 사용자의 승인을 받은 뒤 별도 작업으로 합니다.
- **운영 Supabase에 절대 쓰지 마세요.** 개발용 DB가 없습니다. 실제 방문자 데이터입니다.
  권한 점검은 `supabase/*.sql`을 읽고 판단하거나, 읽기(GET) 요청까지만 하세요.
  쓰기 권한이 열려 있는지 실제로 시험해야 한다면 **보고서에 "이렇게 확인해 보세요"로 적고 멈추세요.**
- push 하지 마세요. 보고서 파일만 새로 만듭니다.

## 산출물

`docs/AUDIT_REPORT.md` 한 파일. 형식:

```markdown
# 점검 보고서 (YYYY-MM-DD, 기준 커밋 XXXXXXX)

## 요약
- 한눈에 보는 3~5줄. 가장 급한 것 위주로.

## 발견 목록
### [P0] 제목
- **어디**: 파일:줄
- **무엇이 문제인가**: (비개발자도 이해할 수 있게 한 문장 + 필요하면 기술적 설명)
- **어떻게 확인했나**: 재현 방법 또는 근거
- **실제 피해**: 누가 무엇을 할 수 있나
- **제안**: 고치는 방법 (가능하면 코드 diff)
...
```

심각도 기준: **P0** 지금 당장(데이터 유출·조작 가능, 사이트 동작 불능) /
**P1** 곧(권한 허점, 눈에 띄는 오작동) / **P2** 개선 권장 / **P3** 취향·정리.

사용자는 개발자가 아닙니다. 각 항목의 첫 문장은 **쉬운 말**로 써 주세요.

## 점검 범위

### 1. 권한·보안 (최우선)

서버 코드가 없어서 **모든 통제가 Supabase RLS에 달려 있습니다.** 여기가 뚫리면 끝입니다.

이미 눈에 띈 의심 지점들입니다. 사실 여부를 확인하고 판단해 주세요.

- **RLS 정책이 두 세대 섞여 있습니다.** `supabase/schema.sql`에는
  `for all to authenticated using (true)` (= 로그인한 아무나 경기·선수·전적을 고칠 수 있음),
  `supabase/schema_remaining.sql`에는 이를 `drop` 후 `is_admin()`으로 교체하는 코드가 있습니다.
  **실제 운영 DB에 어느 쪽이 살아 있는지 확인**하고, 확인 방법을 사용자에게 알려 주세요
  (사용자가 Supabase 콘솔에서 직접 볼 수 있게).
- **`predictions` / `ratings`의 update 정책이 `using (true)`** 로 보입니다.
  그렇다면 방문자가 **남의 예측·평점을 덮어쓸 수 있습니다.** 확인 필요.
- **익명 사용자가 `profiles`의 `is_admin` 컬럼까지 읽을 수 있습니다**
  (anon 키로 REST 호출 시 반환됨). 누가 관리자인지 노출됩니다. 위험도 판단 필요.
- **1인 1표가 어떻게 보장되는가**: `assets/store.js`의 `voterId()`는 비로그인 시
  localStorage 임의 문자열입니다. 지우면 새 표가 됩니다. 예측 포인트·팬심 평점·POG 결과가
  얼마나 쉽게 조작되는지, 막을 현실적인 방법이 있는지 평가해 주세요.
- **글쓰기**: `posts` insert 정책이 길이만 검사합니다. 비회원이 닉네임을 "운영자"로 적어
  사칭할 수 있는지, 팀 게시판 쓰기 제한(팬 회원만)이 화면에서만 막히는지 서버에서도 막히는지 확인.
- **`site_settings` 쓰기 권한**: 로고(데이터 URL, 최대 600KB)와 중계 링크가 여기 저장됩니다.
  관리자가 아닌 사람이 쓸 수 있으면 로고 교체·링크 바꿔치기(피싱 주소 삽입)가 가능합니다.
- **XSS**: 코드 전반이 `innerHTML` + 템플릿 문자열입니다. 사용자 입력(닉네임·글 제목·본문·댓글·
  중계 링크 주소)이 `esc()` 없이 들어가는 곳을 **전수 조사**해 주세요.
  특히 `assets/board.js`, `live.html`, `assets/app.js`의 렌더 함수들.
- 외부 링크: `target="_blank"`에 `rel="noopener noreferrer"`가 빠진 곳.

### 2. 데이터 정합성

- 승부예측 채점(`predictions`)과 순위 반영(`applyMatchToRecords`)의 이중 반영·누락 가능성.
- 낙관적 쓰기(캐시 먼저 수정 → 서버 비동기 저장) 실패 시 화면과 DB가 어긋나는 경우.
  실패해도 사용자에게 아무 표시가 없는지 확인.
- 스냅샷(localStorage) 때문에 **옛 데이터가 보이는 상황**의 범위. 특히 로그인 상태를 스냅샷에서
  복원하는 부분(`snapshotLoad`)이 만들 수 있는 착시.
- KST 날짜 처리(`fmtDayKey`, 마감 시각 비교)가 자정·서머타임 경계에서 맞는지.

### 3. 성능

- 지금 구조: 페이지마다 **모든 테이블 전체**를 받습니다(`fetchAll`). 게시글·댓글·평점이 늘어나면
  언제쯤 문제가 되는지, 어디부터 페이지 단위로 나눠야 하는지 판단해 주세요.
- `docs/AI_HANDOFF.md`의 "열린 항목" 3·4번(Vercel 캐시 헤더, `?v=` 자동화) 검토.
- 이미지: `assets/brand/*.png` 용량, 팀 로고 SVG, Data Dragon 아이콘 개수.
- localStorage 스냅샷 크기 한계(현재 약 29KB, 상한 5MB)와 초과 시 동작.

### 4. 모바일·반응형·접근성

- 375 / 390 / 414 / 768px에서 가로 잘림·겹침. (최근 점검했지만 놓친 화면이 있을 수 있습니다:
  글쓰기, 글 보기, 로그인, 팀 게시판, 관리자)
- 터치 대상 크기(팬심 평점 버튼은 27×24px — 더 키울 여지가 있는지).
- 색 대비, `alt` 텍스트, 키보드 조작, 아이콘만 있는 버튼의 레이블.
- 라이트 모드에서 깨지는 곳 (다크 모드 위주로 만들어졌습니다).

### 5. 코드 품질·유지보수

- 중복된 렌더 코드, 죽은 코드, 쓰이지 않는 CSS.
- `assets/store.js`가 800줄로 커졌습니다. 쪼갤 가치가 있는지(빌드 도구 없이 가능한 선에서).
- 에러 처리: 네트워크 실패 시 사용자에게 보이는 것이 있는지.

### 6. 그 외

- SEO·메타: 페이지별 title/description, og:image 경로, sitemap 유무.
- 법적 고지: 푸터·`terms.html`의 비제휴 문구가 모든 페이지에서 실제로 노출되는지.
- 개인정보: 수집하는 항목(이메일·닉네임·응원팀)과 약관 내용이 일치하는지.
